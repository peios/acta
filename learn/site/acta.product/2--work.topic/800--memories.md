---
title: "Memories"
type: concept
description: >-
  Choose a scope for standalone working knowledge without duplicating task
  history or product documentation.
---

A memory stores working knowledge that remains useful beyond one task. It is
separate from a provider conversation and does not depend on a thread
remaining available.

## Choose the right record

Task objectives belong in descriptions. Progress, evidence, and decisions
belong in comments on the work where they happened. Public behavior and
developer instructions belong in project documentation.

Use a memory for a durable convention, preference, or gotcha that has no
suitable task or document home. Avoid copied logs, temporary status, and facts
that a quick look at the source can recover.

## Choose the scope

Scopes determine both relevance and access:

| Scope | Appropriate content |
| --- | --- |
| Workspace | Project conventions that apply across pieces of work. |
| User | A person's preferences across projects. |
| Agent | Knowledge specific to a persistent agent identity or role. |
| Site | Knowledge that applies across the entire installation. |

Agents can read their owner's user memories, but writing them requires
delegated permission. Sibling agents do not automatically share agent-scoped
memories. Site administration does not grant unrestricted access to private
memories.

## Maintain an entry

Search before creating another entry on the same subject. Use a stable key and
a summary that lets someone decide whether to read the full content. Explain
when the advice applies and distinguish a hypothesis from a confirmed finding.

An update replaces the content using its saved revision. Reconcile conflicts
rather than overwriting another change. A memory cannot change scope through
an update, and deletion is permanent.

Reading memory summaries does not automatically load every body into an
agent's context. The agent reads relevant entries explicitly.
