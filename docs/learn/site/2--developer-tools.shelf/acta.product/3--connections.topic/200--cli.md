The Acta command-line client uses a named profile for a server URL and
credential. Profiles let you work with separate installations or identities
deliberately.

## Before you start

Obtain the `acta` client from a trusted build. For a local source build,
`tools/export` writes it to `bin/acta`. Use the installation's
canonical HTTPS origin; loopback HTTP is supported for development.

## Authorize a profile

For a local development server at port 8081:

1. Run `bin/acta login localhost:8081` from the built checkout.
2. Open the printed browser link if the client does not open it automatically.
3. Sign in, check the device code, and select the intended **Act as**
  identity.
4. Approve the connection.
5. Run `bin/acta whoami` and check the returned identity.

A machine label is descriptive; it is not proof that a request came from a
trusted device. Visiting the authorization link alone does not grant access.

## Select a profile

The `default` profile is an ordinary initial profile. Create additional
profiles with `profile add`, select one with `profile use`, or pass
`--profile` for one command. Creating a profile does not switch the active
selection. An unknown profile is an error, not a fallback to another identity.

Use `status --json` to inspect the server, identity, and credential source
without printing the secret. Use `logout` to revoke the connection and remove
its saved credential. The profile's server URL remains.

## Headless access

Use `--no-browser` when the terminal cannot open a browser. A human still
completes the printed authorization flow. `ACTA_TOKEN` can supply a credential
without saving it, while the profile supplies the server. Do not extract
another application's token to bypass authorization.

The client prefers the operating system's credential store. If saving there
fails, it reports a private plaintext credential file. Protect that file as a
credential. See the [connection
reference](~acta/technical-reference/connections/cli) for storage, expiry, and
retry behavior.
